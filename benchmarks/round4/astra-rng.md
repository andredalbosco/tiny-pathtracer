# Astra RNG recommendation: opt-in xoroshiro128++

Test **xoroshiro128++ 1.0** behind the proposed compile-time option, retaining PCG32 as the default until integrated timing and sample-quality checks justify a change. It is a small, plausible experiment: two 64-bit state words preserve Random's 16-byte representation, and the hot transition uses additions, XOR, shifts and fixed rotations instead of PCG32's general 64-bit multiply and data-dependent output rotation. This is an instruction/dependency hypothesis, not a measured renderer speedup.

The authors' reference uses output `rotl(s0+s1,17)+s0`, followed by `s1 ^= s0`, new `s0 = rotl(s0,49) ^ s1 ^ (s1<<21)` and new `s1 = rotl(s1,28)`. Use unsigned 64-bit arithmetic and a helper valid for these nonzero fixed rotation counts. The all-zero state is forbidden; the authors recommend SplitMix64 to expand a 64-bit seed. Preserve the public-domain attribution/notice when adapting their implementation. [Author reference](https://prng.di.unimi.it/xoroshiro128plusplus.c)

Keep `next()` returning the **upper 32 output bits**, and retain `uniform() = float(next() >> 8) * 2^-24`. This uses the upper 24 bits of the original 64-bit output and keeps the existing exact [0,1) float grid. Do not cast the full 64-bit integer to float and then scale: float rounding can produce 1.0. Retain a known-answer test of the full transition before truncating its result.

## Seeding is part of this benchmark

A path is still identified by `(pixel<<32)|sample`, independent of worker and lane. Do not feed raw `master_seed + path_id`, or raw `master_seed XOR path_id`, into a final hash. Addition creates exact equivalences such as `(seed S, sample j)` and `(seed S+1, sample j-1)`; XOR can simply permute the same short range of sample IDs across adjacent seeds. This would invalidate the intended independent seed replicates, even if each individual image looked random.

A compact starting design is:

1. Mix the master seed with a fixed documented domain constant using the SplitMix64 finalizer.
2. XOR that mixed master key with the full 64-bit pixel/sample identity.
3. Treat the result as a SplitMix64 state and take two consecutive SplitMix64 outputs as the xoroshiro state words.

For a fixed master seed, the XOR mapping is one-to-one over path IDs, and the SplitMix64 finalizer is a permutation of 64-bit words. Consecutive outputs from its distinct counter states cannot both be zero. A defensive all-zero assertion or fallback is still inexpensive. Across master seeds, this is hashed initialization, **not a proof of disjoint or statistically independent xoroshiro subsequences**. Record the exact seeding formula and constants as part of the RNG identity. The authors specifically recommend using a different type of generator for initialization to reduce similar-seed correlations. [Seeding guidance](https://prng.di.unimi.it/), [SplitMix64 source](https://prng.di.unimi.it/splitmix64.c)

Each SplitMix64 output requires two 64-bit multiplies, so filling both words costs four. Mixing the master seed costs another two unless it is hoisted once per render or worker. In contrast, the current PCG seeding code's first warm-up starts at zero and its outputs are discarded: optimized seeding can reduce to **one effective 64-bit multiply**, rather than two full random-generation calls. Inspect the generated code before assigning a setup cost. The current PCG algorithm and 16-byte state match the documented minimal XSH-RR generator. [PCG minimal implementation](https://www.pcg-random.org/download.html), [PCG seeding API](https://www.pcg-random.org/using-pcg-c-basic.html)

The extra setup cost matters because this renderer constructs millions of short path streams. Uniform continuation draws two values per diffuse visit; NEE/MIS normally draw five, plus the two camera values per path. Thus the crossover may differ by estimator. Benchmark seed-plus-short-sequence workloads, such as 2/16/32/64 draws, as diagnostics rather than only a long-running generator. The full renderer remains the acceptance benchmark. If a mixed master key is cached, make that explicit so setup is counted honestly and the PCG baseline keeps its original seed semantics.

## Representation and alternatives

The existing `state` and `increment` fields can temporarily hold the two xoroshiro state words under the macro; document that both are mutable in this mode. PathsSoA already transports both words and needs no extra per-path field. Assert Random's size and verify Path's size remains unchanged. The equal footprint does not guarantee equal traffic: PCG updates one state word while its increment is fixed; xoroshiro updates both. Inlining and register allocation determine whether that becomes additional loads/stores in this renderer.

Prefer this one ordinary-C++ candidate before adding intrinsics or a common virtual RNG interface. Fixed shifts/rotations give the compiler a straightforward hot function. If xoroshiro128++ disappoints, xoroshiro128** is a narrowly related same-footprint follow-up, with a different transition and a small-constant output scramble; it must use its own reference constants and tests. Do not silently substitute the older `+` generator, whose documented statistical properties differ. A four-word xoshiro128 generator would also occupy 16 bytes, but would require more representation changes here and is not the simplest first comparison. [xoroshiro128** reference](https://prng.di.unimi.it/xoroshiro128starstar.c)

## Acceptance checks and limits

- **Implementation and transport:** compare known answers against the authors' algorithm for explicit states and independently check SplitMix expansion. Exercise zero, maximum, adjacent and widely separated master/path IDs. Copy/save/restore state; require identical continuation after an AoS/SoA round trip. Confirm no all-zero initialized state and uniforms strictly below one.
- **Many short streams:** compare full initialized state pairs across a representative grid of pixels, sample IDs and replicate seeds. In particular test adjacent seeds and adjacent samples to catch the aliasing traps above. Interleave first/second/k-th outputs from many short streams, and compare neighboring pixel/sample pairs. Repeated 24-bit uniform values are expected and are not evidence of stream collision; check full states or sufficiently long output tuples.
- **Empirical randomness:** record uniform moments, bins and serial/cross-stream correlations as smoke tests, then run an established statistical suite if practical on both long output and the short-stream layout actually used. Passing a small histogram, correlation check or rendering test is not a claim that a full statistical battery was run. The authors' published test results concern their generator and harness; they do not automatically validate this seeding/truncation/multistream integration.
- **Renderer determinism:** within each RNG, require strict image identity across worker counts, runtimes, batch sizes and refill scheduling. Different RNGs intentionally produce different images and generally different live-ray counts. PCG/xoroshiro image bit parity is not an acceptance condition.
- **Useful image quality:** repeat the quality comparison with independent replicate seeds against the common reference. Report mean-image agreement, MSE, time and MSE×time. Avoid declaring one RNG better from one lucky noise realization or from a smaller MSE against a reference sharing its seed streams.
- **Integrated performance:** compare PCG and xoroshiro with matched source, estimator and arithmetic flags on one P core, one E core and all CPUs. Train PGO separately with the same protocol. Preserve binary/source/seeding hashes and label the RNG in output metadata. Record ray/shadow work; different random paths can change the workload. Perf may explain instruction/load changes, but a generator-only benchmark cannot predict the full renderer gain.

The authors qualify 128-bit xoroshiro as suitable for limited-scale parallel use. Thirty-two hardware threads alone does not resolve that question: this application initializes millions of distinct short paths across a render. Hash-based startup should not be advertised as the authors' jump-based nonoverlap guarantee. The provided jump function is a different construction, and performing a full jump for every short path would undermine this small setup-cost experiment. Published generator speed numbers use another CPU/compiler/harness; they are not measurements of this i9-14900K renderer. [Authors' scope and benchmark caveats](https://prng.di.unimi.it/)

The preceding quality audit is complete in `astra-results.md` and explicitly distinguishes the audited prototype from the pending final rerun. No source files, defaults or CPU benchmarks were changed for this RNG recommendation.
